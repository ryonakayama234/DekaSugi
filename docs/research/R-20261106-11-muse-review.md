## 3. 逆質問への回答（QG-RQ1〜RQ3）

**RQ1（512 MB の単位）— 結論: SI 512,000,000 bytes で確定してよい。**
根拠: 凍結本文は単位系を明記しておらず、より厳しい読みを採ることは自己都合の緩和にはならない。解釈を実装・測定の前に書面で固定すること自体が要件であり、本回答をもって G3 実装仕様として確定する（凍結した上限値そのものの変更ではない）。比較は bytes で行うこと（ru_maxrss の KiB を ×1024 してから 512,000,000 と比較）。報告値は個別 child の wait4 peak RSS のみとし、cgroup の memory 値は別の group 指標として記録し、process RSS と同一名で報告しない点にも同意する。STOP 条件: RSS が測定不能な環境では当該次元は UNMEASURED であり、上限適合を主張しない。

**RQ2（CPU hard cap の実効性）— 結論: 「測定が正本」の定義で受容する。**
根拠: RLIMIT_CPU の粒度ゆえ、強制の成否で適合を判定すると、制限器の不完全さが黙った PASS を生む。適合判定は終了時の wait4 実測（ru_utime+ru_stime）で行い、実測が 5 秒を超えた child は制限器の動作にかかわらず RESOURCE_STOP とする。RLIMIT_CPU と親 watchdog は最良努力の強制として併用する。これにより「hard cap」は「上限を超えた結果は数えない」という運用定義として厳密になる。環境についても fail-closed に同意する: 個別 child の CPU/RSS が測定できない環境では実行しない。cgroup については注記1 の扱いとする。Owner 決定は不要（凍結の解釈の範囲）だが、G4 で実効性の故障注入結果を監査する。

**RQ3（FIXED-MACRO import の交絡）— 結論: 生値開示を採用し、A では局所 refactor を行わない。**
根拠: 本測定の対象は「現行の配線のままの費用」であり、対照 arm の import 構造を最適化すると測定対象そのものが変わる。交絡は import する全プロセスに同種に発生し、計画の方式（per_fresh_process の実測として記録し、差し引かない、one_off 列は実際に事前構築した場合のみ・未実施なら UNMEASURED）で正直に扱える。同等性の事前査読つき refactor という代替案は、検証コストに見合う会計上の利得がなく、むしろ「最適化された対照」との比較という別の主張を招く。認める反例: もし科学用 child の入口が arm ごとに異なる import 経路を辿り、交絡が非対称になる場合は、その非対称自体を G4 で監査し、入口の統一（意味論を変えない範囲）が必要になる。これは refactor の許可ではなく監査項目である。新規 `r2_m_a` 内部の構造は自由であり、本回答が禁じるのは再利用する `r2_m_eng` 側の意味論・import 挙動を測定対象として変えることだけである。
