## 0. 前提と経緯

### 0.1 DekaSugi とは・固定条件（変える提案はしない）

- 研究対象: 小さな中枢が、外部の知識・技能・道具を再利用しながら、新しい操作体系（操作言語）を自分で拡張していけるかを検証する研究。リポジトリは本 repo（ryonakayama234/DekaSugi、public）。

- 初期実験で巨大な事前学習 LLM は使わない。記号的学習とパラメータ学習は区別して進める。知能は静的な蓄積物ではなく動的なプロセスの中にある、という Owner の知能観を前提にする。
- 役割分担: ChatGPT が調査・研究・実装・処方の起草、監督者（Muse）が広い視点での検証と大局管理、Owner が決定。マージ・実装 GO・実験 GO は都度 Owner の明示決定が必要で、回答側の「承認」「GO」表現は決定として扱わない。

- 語彙: 本 repo への文書では、身体部位等に触れる場合も科学的／解剖学用語で統一する（本票では該当箇所はない想定）。

### 0.2 ここまでの実験と結果（本票の判断材料）

- 実験A（道具化・費用の軸）は閉じた。経験で得た技能に費用優位は観測されなかった。
- WORLD-LEAN-1（小さなテキストエディタ世界で、経験から獲得した技能が未見課題の探索を改善するか）: 正式評価で FULL（技能を使う）91.2%／OFF 90.6%／STATIC-RANK（静的対照）90.5% とほぼ同成績。判定は STOP_DIAGNOSTIC。獲得技能の追加価値は示されなかった。解釈として「課題が既存能力だけで解けてしまう構造だった可能性」が残った。
- SENTENCE-REVISION-1（短文＋訂正の経験で、未見状態での実行規則が改善するか）: Owner が4ケース×6例の選択と訂正文を2回のセッションで作成し、監督者が固定・1回だけ本番実行した。結果は、改訂対象3件中2件（R02・R03）で未見正答が2/3→3/3に改善し初期正答の喪失なし。ただし全履歴から再合成する FRESH も全ケース同成績で、REVISE 固有の優位は未実証。確認対照のはずの R04 は、初期規則が訂正例を誤予測していたため「改訂不要の対照」として機能していなかった（監督者の固定前検査の不足として記録済み）。

- 進め方への診断（Owner・監督者・ChatGPT で概ね一致）: 再現性を守る仕組み（事前登録・封印・独立審査・複数段の PR）が探索の回転速度を落としている。軽量化として「1実験＝問い1つ／探索ランと認定ランを分ける」等の一部は採用済み。main の最終コミットは 11月10日で、成果の多くは Draft PR に滞留している。

### 0.4 Owner の違和感と提案（本票の核。2026-11-16、提案であり未決定）

- 違和感: 「昨日の ABCD のルール決めのような抽象課題は、自分の元のイメージと全然違う。役に立たない抽象を弄くっている感じがする。抽象では、何が起きているのか、どう発展しているのか、何に詰まっているのかを自分が判断できない。」
- 「テキストエディタ世界にしよう」と言ったときの本来の意味: 例えば Owner が実際の操作意図・目的を持って（SNS に投稿する文章の下書きなど）メモ・文章入力をする場所。その入力の時間発展（次の文字・単語の選択の列そのもの）がエピソード＝学習データセットになり、ある程度の能力が獲得できるのではないか、という仮説。完全な自然言語能力には別途の能力検討が必要だろう、という留保は Owner 自身が付けている。
- もう一つの軸: 3Dモデリング用プログラミング言語のエディタで書く経験（プログラム知識＋モデリング）。プログラミング言語は規則が固い（AST 等で構造が決まる）分、自然言語より学びやすい可能性がある、という Owner の見立て。なお Owner はプログラミングの詳細には習熟しておらず、コード自体は読めない。
- 物語（ストーリー）の案: 基礎言語を作る → エピソード・経験を貯める → Skill・記憶・Tool 等へ外部化する（中心の負担を減らす）→ ブートストラップ → 基礎から発展言語・発展記号を作る → 日本語や 3Dモデリングの性能を上げる → 日本語や 3Dモデリングの外にも適応できる記号系を発見する。自然言語（日本語）軸とプログラミング言語軸のどちらから始めるかは、Owner にもまだ分からない。
- スタートの形: テキストエディタ／モデリングエディタのどちらから始めるかはともかく、「書ける HTML エディタでデータを作るスタート」が良いのではないか。
- 判定可能性（Owner の条件）: 「日本語を書く」話なら Owner が判断できる。「モデリング言語を書く」話は、コードは Muse／ChatGPT が読んで評価でき、出来た 3D モデルの評価なら Owner ができる。双方とも課題は作りやすいはずだ、という見立て。
- 進捗の物差し: 「DekaSugi に出来ることを増やしていくのがいい、と思いたい」（確定ではなく提案）。つまり進捗は、抽象的な指標の改善ではなく、目に見える能力の追加で測りたい。

### 0.5 関連する既存の材料と資産

- 「文の経験」メモ（2026-11-14、Owner 提起・預かり）: エディタ世界で Owner が文章を書く＝機械の代わりに文章記述の経験を作る、という本提案の日本語側の前身。監督者の整理では、正例だけでは文法は一意に同定できず意味も接地しないため、成立に近づける要素は (1) バリエーション（1か所だけ違う文の組から枠＋スロットを発見する）(2) 直し（生成→Owner の修正→規則の書き換え。負の証拠になる）(3) 世界との対応づけ（操作と説明文のペアで接地し、生成・実行を最終状態で決定的に検証できる）の3点。一般の日本語作文は LLM 規模のパラメータ学習の領域で現行方針の外、という線引きも同メモにある。本提案はこのメモより広く、実際の目的を持った入力から始める点と、外部化→ブートストラップの物語が明示された点が新しい。
- 既存の実装資産: 小さなテキストエディタ世界の実装（バッファ＋カーソル＋選択範囲、原子操作、条件の文法、候補規則の列挙と訂正による絞り込み、決定的な採点器）。SENTENCE-REVISION-1 の固定・採点の仕組みも含む。再利用できる部分と、本提案では捨てるべき部分を回答で切り分けること。
- 常設レンズ「Continual-ARC」（Lenton, arXiv:2611.14505。数値の一部は二次まとめ経由で、正式引用には本文再照合が必要）: 「経験した」ことは「学習した」ことではない。何を残すかの判断、残したものの検証、再訪時に頼まれなくても取り出す仕組み、の3点が揃って初めて経験は次回を安くする。評価では記憶（見た課題での節約）と汎化（未見での伸び）を分け、記憶を消した対照を見る。本提案の「外部化」の設計にもこの3点検を適用すること。
- Maccho（描画 AI、別企画）との同型性: Owner の手作業アノテーション（1筆の区切り＋1文の指示文キャプション）が Phase 3（指示→描画）の種データになる設計が既に動いている。「本人が目的を持って作った行為の記録が、後段の学習の種になる」供給方法の先例として参照してよい。

4. 既存線の扱い: (d) 短文の意味付け、待機候補「新しい区別の発見」、3D 側 S1／S2 線を、本提案の下でどう置くか（QB7）。

## 2. 質問

- **QB1（開始軸の選択）**: 日本語テキストエディタ軸／モデリング言語エディタ軸／共通基盤先行の3案を、同じ評価軸で比較すること。評価軸は少なくとも: Owner の判定可能性、データ供給の持続性（Owner が実際に書き続けるか。日常の文章書きと、頼まれた課題書きでは供給がどう違うか）、検証の決定性（結果が正しいかを機械が言えるか）、学習対象の難しさ（規則の固さ・曖昧さ）、ブートストラップの見込み、既存資産の再利用度（文訂正の実装群／3D の S0・S1／S2 線）、最初に「出来ることが増えた」と Owner に見えるまでの速さ、失敗したときの残るもの。推奨を1案に絞り、推奨が覆る条件（何が見えたら他軸へ切り替えるか）も明記すること。表形式で示すこと。
- **QB2（基礎言語とエピソードの設計）**: 推奨する開始軸について、基礎言語の最小設計を示すこと。与えるもの（語彙・文型・原子操作・文法の枠）と、経験から獲得させるもの（対応・規則・技能・記号）の線引きを根拠つきで述べること。あわせてエピソードの形式を具体例つきで示すこと（1件に何が入るか: 目的・意図の記録方法、入力の時間発展の記録粒度、直し・取り消しの扱い、最終成果物、自動で付けられる評価、後から人が付ける評価）。日本語軸なら「目的を持った実入力」と「学習のための課題入力」の混ぜ方、モデリング軸なら既存の S0 エピソード叩き台との差分も述べること。

- **QB3（外部化のループ）**: 貯まったエピソードから Skill・記憶・Tool へ外部化するループを設計すること。何が・どの単位で・どの検証を通って外部化物として採用されるか、採用された外部化物が次の入力・生成でどう取り出されて使われるか、使えなかったときにどう直されるか。Continual-ARC の3点検（残し方の明示／検証済みで実行可能な形／再訪時に頼まれなくても取り出せるか）を各段階に適用すること。記号的な外部化（規則・プログラム・対応表）とパラメータ的な学習（並びの統計等）のどちらを主とし、どちらを従とするか、現行方針（巨大 LLM を使わない）との整合も述べること。
- **QB4（ブートストラップの段階）**: 基礎言語から発展言語・発展記号へ進む段階を提案すること。各段階について「新しく出来るようになること（Owner が見て判断できる具体的な出力・デモ）／その段階の入口条件／出口条件と止める条件／外部化物がどう増えるか」を表で示すこと。最終段として「日本語・3Dモデリングの外へ適応できる記号系の発見」を置く場合、その段で何が見えれば発見と言えるのかの判定形も示すこと。段階は大きくしすぎず、最初の2段階は数週間で到達を判断できる粒度にすること。
- **QB5（能力が増えたと言える測り方）**: 各段階で「出来ることが増えた」をどう測るか。未見課題での実行、記憶と汎化の分離、経験なしの強い対照との比較、外部化物を無効化したときの性能差（アブレーション）を、探索ラン（小さく速く失敗できる）と認定ラン（主張に使う厳密な測定）の分離を前提に、段階ごとに軽重をつけて設計すること。WORLD-LEAN-1 の教訓（対照が天井に張り付く課題では測れない）を避けるための、課題側の事前確認の置き方も含めること。

- **QB6（最初の制作物: 書ける HTML エディタ）**: 最初に作る HTML 一枚のエディタの最小構成を提案すること。含めるもの／含めないものの線引き、自動で記録される範囲（キー操作・確定・直し・保存のどこまでをどう残すか）、書き出し形式、Owner の実入力（SNS 下書き等、個人的な文章）を扱う前提での保存先とプライバシーの扱い（既定はローカル保存・外部送信なし）、Owner の負担（1回の入力で余分に求める操作があるか）を見積もること。制作の段取り（誰が何を作り、監督者が何を検証するか）と、最初の使用シナリオ（使い始めて2〜4週間で何件ほどのエピソードが現実的に貯まる見込みか、その根拠）も示すこと。
- **QB7（既存線の扱い）**: 次の3件について、本提案を優先した場合の扱いを、それぞれ「続ける／保留する／縮小して吸収する／中止する」のどれかと根拠で答えること。(i) (d) 短文の意味付けカード（起草済み・Draft PR #226）と、同日採用した停滞感対策の補足。(ii) 待機候補「新しい区別の発見」。(iii) 3D 側の S1／S2 実装計画線（モデリング軸を選ばない場合の置き方／選ぶ場合の合流の仕方を含む）。あわせて、大目標Bと登録済みサブ目標の地図がどう変わるか（変えない部分も含め）を1枚の対応表で示すこと。
- **QB8（登録できる形・失敗条件・判断点）**: (a) 本提案の下で Goals に登録するサブ目標の候補を3〜6件、「タイトル／1行の現在地／2〜3文の説明／完了の定義」がそのまま登録文に使える形で提案すること。(b) この路線全体の失敗条件と、途中で縮小・転換すべきサイン（例: データが貯まらない、外部化しても能力が増えない、Owner が判断できない成果しか出ない等）と、各サインへの対処を示すこと。(c) 末尾に Owner 判断点 M1〜 を整理すること。
