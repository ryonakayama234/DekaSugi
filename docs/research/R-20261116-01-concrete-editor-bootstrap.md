## QB1 — 日本語の実入力を入口にする

### 同じ軸での比較

| 評価軸 | 日本語テキストエディタ | モデリング言語エディタ | 共通基盤を先に作って分岐 |
|---|---|---|---|
| Ownerの判定可能性 | 読みやすさ、意図どおりか、自分の直し方かを直接判断できる。ただし正解は一意でない | 形状は判断できる。AST・コードの正しさはChatGPT/Museが担い、コードだけの成果は見えにくい | 基盤単体には生活・制作上の完成品がなく、判定が再び実装者寄りになる |
| 日常入力と課題入力の持続性 | 普段のSNS下書き・メモに使えれば自然に供給される。依頼された例文だけでは供給負担が高い | 実際に作りたい形があれば続く。現状は操作習得・課題制作・コード補助が必要で、日常的な書き手が未成立 | 両方に供給源があることを確かめる前に共通化すると、データなしの基盤が残りやすい |
| 検証の決定性 | 文字列・履歴再生・形式制約は決定的。文章の良さと意図適合には人の判定が要る | 型・再生・指定寸法・幾何条件は決定的。美観や用途への適合は人が判断 | 共通形式の整合性は測れるが、能力の正しさは各領域の検証器に依存 |
| 学習対象の難しさ | 自由作文は広く曖昧。範囲を「本人の訂正の再利用」に絞れば小さく始められる | S0の有限操作は意味が明確。ただし規則が固いことと、目的からよい形状を選ぶことの容易さは別 | 共通表現・両領域adapter・学習の三つを同時に設計する難しさがある |
| ブートストラップの見込み | 訂正片→置換枠→文脈付き操作→組合せ、の順で目に見える。ただし少量入力から日本語全体への飛躍は見込まない | 操作列→部分形状関数→制約付き生成を検証しやすい。ただしAIが書いた定型プログラムの蓄積だけでは中枢の獲得を示さない | 後日の移植には役立つが、最初の獲得に必要なループを先送りしやすい |
| 文訂正の既存資産 | 状態遷移・原子操作・訂正履歴・採点分離を再利用しやすい。小バッファ世界は実入力UIへそのまま移せない | 来歴・採点分離の考え方は使える。文字世界の操作意味は形状世界へ移せない | 実績のある差分だけを共通化できれば有用。最初から統一する根拠はまだない |
| 3DのS0・S1/S2との関係 | S0は将来の第二領域の契約として保持。S1/S2を今回の先行条件にしない | S0の4演算を直接土台にし、S1/S2と合流できる。ただし現在は仕様受入・計画段階で、完成エディタがあるわけではない | S0とテキストの本当の共通部分を実測する前に抽象層が肥大するおそれ |
| 「出来ることが増えた」が見える速さ | まず書く・直す・戻すが見える。次に別の下書きへの訂正候補提示。後者の成立速度は反復の有無次第 | 形状が出れば見えやすいが、言語入力・レンダラ・保存再生までが入口。手書きのデモ形状と学習成果を分ける必要 | 初期には基盤しか見えず、現在の停滞感への処方として弱い |
| 失敗して残るもの | 実用下書き帳、本人が所有する訂正付きコーパス、履歴再生器。学習未成立でも利用価値がある | 訂正できる最小工房、再生可能な形状プログラム、幾何検証器 | schemaやadapterは残るが、両領域で使われなければ保守物になる |
| 今回の順位 | **第一候補**。供給と本人の判断を研究の入口に置ける | 第二候補。目的ある制作の供給が確認できた場合の転換先 | 先行しない。共通化は第二領域で必要が見えてから |

推奨理由は「日本語のほうが一般に学習しやすい」からではない。現時点で目的のある行為をOwnerが自然に供給でき、よしあしを直接判断できる見込みが最も高いからである。モデリングの文法の固さは検証を助けるが、書き手・制作意図・学習信号まで自動的には用意しない。

一方、日本語入力の時間列だけから目的や意味が同定されるとは仮定しない。最初は記録を広く取り、学習対象は実際に再出現した訂正の一種類に絞る。自由作文を狙って巨大モデルや大量の課題入力を追加する方向へは進めない。

### 推奨が覆る条件

初回使用から2週間を目安に供給を点検する。実入力が3件未満、または普段の下書き帳へ戻ってしまうなら、まず保存・操作の摩擦を直す。使う必要自体がなければ記録器を縮小し、「毎日書く」義務は設けない。

2〜4週間使っても、同種の訂正が別の下書きに現れず、短い確認課題もOwnerの負担になるなら、日本語の学習線を保留する。その時点で、**実際に作りたい形が複数あり、コードを読まずに形と修正意図を示せるか**を確認し、成立するならS0準拠の3D線へ転換する。単なるデータ不足を理由に、まだ供給のない第二領域へ自動で移らない。

共通基盤先行へ変えるのは、両領域の実用プロトタイプが既にあり、同じ保存・版管理処理の重複が支障になった場合に限る。能力差が出ないだけなら、基盤を増やす前にQB5の課題と対照を点検する。

## QB2 — 書き言葉を小さな人工文法に置き換えず、行為の足場を与える

### 与えるものと獲得対象

ここでいう基礎言語は、当初から日本語の意味体系を設計者が配るものではない。日本語の文字列を操作し、訂正の前後と結果を照合できる、最小の行為表現である。

| 層 | 設計者が与えるもの | 経験から獲得させるもの・獲得とは呼ばないもの |
|---|---|---|
| 表記 | Unicode文字列、改行、範囲、カーソル、選択、版付きのオフセット規約 | 文字コード・IME・カーソル操作自体は与えた機構。日本語理解の獲得とは呼ばない |
| 原子行為 | `replace_range(start,end,text)`、`set_selection(anchor,focus)`。挿入・削除はreplaceの特殊例。保存・復元・評価は管理イベント | どの範囲を何へ直すか、どの操作列を再利用するか。任意JavaScriptやPythonの生成実行は許可しない |
| 候補の構文 | 文字列定数、変数スロット、連結、前後の文字列一致、条件付き適用、有限個の操作列を表す型付きAST。最初から全機能を実装しない | 定数、スロット境界、共有される前後文脈、適用条件の組合せ。設計者が正解テンプレートを埋め込んだら獲得ではない |
| 学習手順 | 差分整列、共通部分を残して異なる箇所を変数化する候補生成、反例で候補を落とす探索手順、上限と棄権 | 例から選ばれた枠・例外・再利用単位。変数化という推論法自体は与えたものと明示する |
| 目的・指示 | 任意の自由記述欄と、本人が選べる「SNS下書き／メモ／その他」程度の用途。空欄も許容 | 指示表現と操作の対応は後段の獲得対象。用途タグを入力すれば目的が理解できた、とはしない |
| 評価 | 再生一致、対象外範囲の不変、文字数・禁止語等の明示制約、本人の採用・修正・却下 | 自動評価器や人の好みをそのまま真理にしない。採用理由が不明なら「好み不明」、評価なしは未評価 |

初めは新しい形態素解析器や基礎日本語文法を作らない。確定文字列の差分から始め、単語分割は必要が現れたら版付きの派生処理にする。原始演算と候補構文が同じなら、学習後の技能追加は操作の圧縮・選択・再利用の拡張であり、計算可能な関数そのものが増えた証拠にはならない。

### 1件の区切りと記録粒度

1件は「一つの下書きを、ある用途で書き始め、区切りとして保存するまで」。一文字ずつを独立サンプルにせず、下書き内の文・訂正箇所を派生単位として取り出す。続きの編集は同じdraftの新revisionとして親を参照し、別の独立課題として数えない。途中終了・破棄も状態として残す。

記録するのは**エディタ内で実際に確定した編集トランザクション**と選択の変化である。キーから次の単語を推測したり、思考・意図を復元できたと扱ったりしない。IME候補窓や内部の変換候補列は取得対象外で、変換前文字列の逐次永続化も既定では行わない。よって得られる時間発展は「確定した文字・句の選択とその訂正」であり、一打鍵ごとの言語選択ではない。

| 要素 | 最小フィールド案・扱い |
|---|---|
| 身元・来歴 | `schema_version, editor_version, episode_id, draft_id, revision, parent_revision, origin`。originは`owner_real / owner_probe / assistant_generated`等。AIの候補と本人の入力を混同しない |
| 目的・意図 | `purpose.text`は任意、未記入を許す。`purpose.source`はowner／unknown。用途、明示された制約、後から追記した時点を残す。実際の投稿先アカウントは収集しない |
| 開始状態 | `initial.text, initial.selection`。空から書いたか、手動で貼り付けたかを区別 |
| 時間列 | 単調増加する`seq`、開始からの相対時刻、`kind, input_type, origin, before_revision, patch, selection_after`。壁時計の精密な時刻は必須にしない |
| 文字差分 | `patch={start_utf16,end_utf16,insert}`。範囲は変更前本文のUTF-16 code unitで半開区間。JSの選択APIと揃え、サロゲートペアを途中で切らない。字数・見た目の一文字とは別 |
| IME | composition中は一時状態。確定後の本文とcomposition開始前本文の差分を一取引にする。中止は本文の最終変化と中止状態を記録し、通常入力と二重計上しない |
| 直し・取り消し | 削除・置換・undo・redo後も同じ形式の差分として追記。原イベントは消さない。履歴イベント種別や対応が取得できなければ`unknown`、勝手な因果リンクは作らない |
| 非逐次操作 | 貼付け・切取り・ドラッグ・音声入力等は取得できたinput_typeと変更結果を残す。クリップボード全体、他アプリ、OSの入力は監視しない |
| 完成品・状態 | `final.text, final.selection, status`。saved／abandoned／interrupted等。初期状態＋確定差分から最終状態が再現できるかを検証 |
| 自動評価 | `replay_match, constraints, content_hash, event_count`等。文章の適切さは未評価のまま。保存したという事実だけを「成功」の教師にしない |
| 人の評価 | `accepted / edited / rejected / unrated`、任意の理由・評価時点・評価対象revision。自分で文章を直した事実と、機械提案への評価を別フィールドで残す |

ブラウザが取りこぼし、差分と本文が合わなければ、隠して「完全な履歴」にしない。直前までの整合区間と、観測された本文の回復snapshot、`capture_gap`を保存する。その区間は最終文の保存には使えても、正確な行為列の学習には使わない。

### 具体例（架空の構造例。実入力・実測ではない）

目的「お願いの下書き」、初期文「資料を確認してください。」に対して、Ownerが語尾を「確認していただけますか。」へ直した例を考える。

```json
{
  "schema_version": "draft-episode/0-proposed",
  "editor_version": "recorder/0-proposed",
  "episode_id": "example-01",
  "draft_id": "example-draft",
  "revision": 1,
  "parent_revision": null,
  "origin": "owner_real",
  "purpose": {"text": "お願いの下書き", "source": "owner"},
  "initial": {"text": "資料を確認してください。", "selection": [3, 12]},
  "events": [{
    "seq": 1, "t_ms": 2400, "kind": "edit_commit",
    "input_type": "insertFromComposition", "origin": "owner",
    "before_revision": 0,
    "patch": {"start_utf16": 3, "end_utf16": 12, "insert": "確認していただけますか。"},
    "selection_after": [15, 15]
  }],
  "final": {"text": "資料を確認していただけますか。", "selection": [15, 15], "status": "saved"},
  "automatic": {"replay_match": true, "semantic_quality": "unrated"},
  "human": {"proposal_rating": "unrated", "comment": null},
  "privacy": {"scope": "local_only", "share_allowed": false}
}
```

この一例から得られるのはまず文字列の直し方の記憶である。別の実入力で「予定を確認してください。」も同様に直され、保持すべき「確認してください。」も観測されれば、共通枠と適用範囲の候補が生じる。未見の対象語でも対象を保って直せるか、適用すべきでない場面で棄権するかを見る。設計者がこの枠を実装した場合は、手製の補助機能の成果として別記する。

削除された表現も常に「日本語として誤り」ではない。誤字修正、内容変更、相手に合わせた変更、気分による変更が混在する。理由を自動で断定せず、使う段で必要な少数例だけ確認する。

### 実入力と課題入力の混ぜ方

既定は実入力のみ。最初の2週間は自然に現れる反復と訂正を観察し、その後、候補があるのに適用範囲だけ不明な場合に限り、任意の対比課題を追加する。目安は全件の0〜20%、週1回5分以内・2〜4件まで。これはノルマではなく負担上限であり、課題入力と実入力の成績は分ける。

課題は空想のABCDではなく、本人が以前書いた依頼文の対象だけを変える、同じ語尾を残したい場面も用意する、といった確認にする。開発のために作った対比課題は探索用であり、そのまま認定用に再利用しない。自然に任せた記録では識別に十分な反例が来ない可能性も、路線の限界として受け入れる。

## QB3 — 外部化は、保存・検証・自動再訪を一周させる

記号的な外部化を主とする。少量の並びの統計や頻度は候補の順位付けの従属情報として後から使えるが、最初のHTMLに学習器は入れない。ニューラル学習や巨大LLMは前提にせず、将来パラメータ学習を試すなら記号的学習と別snapshot・別対照で評価する。

質問票のContinual-ARCの3点検を、以下では設計レンズとして用いる。原典本文をこの回答で検証したという意味ではなく、論文の数値・効果を引用しない。

| 段階・単位 | 何を残すか | 検証済みで実行可能にする方法 | 再訪時の取出し・失敗後の修正 |
|---|---|---|---|
| 観測の保存: エピソード | 本文、確定差分、目的の出典、訂正・棄却・欠測、機械提案の来歴 | 再生一致・範囲・版を確認。不整合区間は除外理由を残す | 本文の局所文脈から関連する過去例を検索。再生不良なら学習候補へ渡さず、原本は残す |
| 記憶: 一つの訂正対 | before→after、観測された文脈、元エピソードへの参照 | 当該例を正しく再現し、他の箇所を壊さない。全文・完全一致だけなら記憶と分類 | 次の下書きの一致箇所で自動的に一候補を示す。「前の例を呼んで」と言わせない。外れた記憶は適用を止める |
| Skill候補: 複数例の共通枠 | 型付きAST、スロット、適用条件、正例・反例、探索手順・予算・版 | 過去例の再現、保持すべき箇所、未使用の開発例で調べ、差分を本人が読める形にする。曖昧なら棄権 | 入力の確定後・短い休止時に文脈索引で照合。最初は1件だけ、全文を自動で書換えない。却下は反例候補で、理由不明の却下は即座の意味ラベルにしない |
| 実用候補としての採用 | 来歴、依存、適用条件、確認済み範囲、ロールバック先 | 小さな開発確認と本人の使用希望で候補提示へ使える。これは科学的な獲得認定とは別 | 関連文脈で自動提示し、採用・編集・却下を次エピソードへ記録。修正は新version、旧版を上書きしない |
| Tool化: 再利用可能な操作API | Skillの固定版、入出力型、前提条件、失敗状態、使用上限 | allowlist原始演算へ展開して検証。循環依存・無限展開・任意コードは禁止。保存・取得費用も計量 | 中枢が前提条件に従って選択する。ボタンを増やしただけなら手動道具。自動選択の寄与は別に検証し、不一致時は前版／原始操作へ戻す |
| 組合せ・次の外部化 | 実際に役立った操作列と依存グラフ、成功・失敗例 | 組合せを原始操作へ展開して結果を照合。自己生成例だけで採用しない | 別の下書きの新しい組合せで使う。誤りの起点を記憶・取出し・条件・操作に分けて直す |

外部化物は `candidate → usable_for_suggestions → evidence_supported` のように、実用の可否と根拠を分けて持つ提案とする。`evidence_supported`も「登録された課題・予算内で」の意味であり、標準Registryへの自動昇格ではない。

このループの初期対象は「局所の入力文脈→直し方候補」。自由記述の目的文を理解する機能はまだない。後段では同じ本文でも目的文を変えると候補が変わるかを調べるが、その対応を人が書いたなら人の供給として数える。自動で検索した記憶の文章を指示として実行せず、実行するのは検証済みのASTだけにする。

外部化を有効にする条件は、同じ文字列の反復だけではない。保持・取出し・適用の失敗を区別できる記録が要る。候補が存在しても取出されない場合は検索の課題、取出されても別の場面で誤る場合は適用条件の課題、そもそも共通性がない場合は学習機会の不足である。

## QB4 — ブートストラップを、見える追加能力の小段に分ける

段0〜1は、制作許可後から最初の利用数週間で到達・停止を判断できる粒度にする。後段は自動的に実施せず、前段の結果を見て別途範囲を決める。

## QB5 — 便利さ、記憶、汎化、形成された区別を分けて測る

### 二つのレーンと段階ごとの重さ

日常利用は探索レーンで、試して直してよい。認定レーンへ進むのは、探索で有用な反復が見え、対照と差を測れる課題が用意できたときだけにする。毎回の下書きに封印やPRを要求しない。

| 段階 | 探索で見るもの | 認定・主張に使うときの追加条件 |
|---|---|---|
| 0 記録器 | 実際に使えるか、再生・復元一致、保存失敗、追加操作時間 | 工学的確認のみ。文章能力・学習の認定はしない |
| 1 訂正の記憶 | 別の下書きでの取出し件数、提示数、採用・編集・却下・未評価、不要な提示 | 記憶を消した対照と完全一致検索を比較し、再訪時の節約として限定報告。未見汎化と混ぜない |
| 2 枠の獲得 | まず6〜12件程度の少数の開発例で、対象保持・誤適用・棄権・差の出る理由を全件で読む | 新しい保留課題、強い経験なし対照、記憶だけ、Skill無効化、FRESHとの比較。主指標・分母・悪化条件・予算を先に一枚へ固定 |
| 3 目的・区別・組合せ | 同一本文で目的を変える、目的を消す、適用しない例、順序を入れ替える | 正しい目的文／入替え／無文の因果比較と、獲得した区別だけの無効化。対応学習と新しい区別の形成は別々の主張 |
| 4〜5 転移 | 第二・第三領域で起きる破綻の分類 | 未見領域への接続情報・手作業・経験量・費用を統制。ゼロから、手製共通枠、記号無効化との比較。ここへ進む段で十分な件数を設計 |

「少数例で一度使えた」と「安定して能力が増えた」を分ける。認定試験の件数は、主張したい範囲と許せる誤適用率・差の精度から別途決め、今回の日常入力件数で検出力があるとは宣言しない。

### 指標と評価入力

構造の正しさは、指定範囲の差分と対象外の不変性、明示制約、再生結果で機械的に採点する。文章の妥当性は複数の解を許すので、完全一致だけにせず「意図に合う／直せば使える／使えない」を、可能なら方式名を伏せてOwnerに判定してもらう。本人の都合で未評価なら欠測のままにする。

主な表示は、方式ごとの「提示／正しく適用／誤適用／棄権／未評価」の件数と、対になった改善・悪化の表とする。提示した箇所だけの採用率で、棄権だらけの方式を優秀に見せない。全予約課題での達成率、保持例の非破壊、提示数、本人の修正量も併記する。時間・操作回数・探索候補数・保存容量は単位を混ぜず副指標に置く。

分割の単位は文字・イベントではなく下書きとその近縁群である。同じ下書きのrevision、同じ文の名詞だけを替えたもの、同じ生成元の言い換えを学習と保留へ散らさない。「未見の対象語で同じ枠を使う」試験と、「未見の場面・枠を組合せる」試験を別欄にする。前者だけで広い日本語汎化を主張しない。

### 経験なしの強い対照と天井の事前点検

経験なし対照には、許可された原始操作・同じ候補構文による探索に加え、用途に適した手製の定型変換や汎用テンプレートを含める。経験あり側の自由な候補探索に対し、OFFを何もしないだけに制限しない。経験ありの完全一致記憶と近傍例の再利用も別対照に置く。逐次改訂の固有利益を主張するときは、同じ経験全件からのFRESHを維持する。

工程は次の小さな一周にまとめる。

1. 探索用の実入力を見て、一種類の反復する編集意図と、保持すべき反例を選ぶ。成功例だけを残さない。
2. **開発専用の課題**で、経験なしの最も強い対照が既に全問を解くか、学習器と違う出力になる機会があるかを点検する。対照が天井なら、その課題は獲得を測れないと記録する。
3. 人が作った正解操作が合法に実行できることも確認する。これは課題の実行可能性の確認で、学習器が到達した証拠ではない。表現不能・候補発見失敗・予算不足・データ不足を分ける。
4. 測れる見込みがある一種類に限り、新しい保留課題、許す入力、方式・予算、採点、欠測、停止条件を固定する。実装レビューとOwnerの実験判断は必要だが、そのための新しい多段機械は先に作らない。
5. 保留課題で一度比較し、全件を返す。保留を見て直したら次版は新しい保留で測る。実用改善用に開発へ戻すことはできるが、認定根拠として再使用しない。

静的対照が天井に達したとき、対照を弱くして差を作らない。本人固有の選好、適用しない場面、経験でしか得られない対応が実在するかを点検する。なければ、便利な既成ツールで足りる領域だったと認める。

### 無効化の切り分け

同じ学習済みsnapshotに対し、(a)Skill実行だけを無効化し記憶・原始探索は残す、(b)記憶の取出しだけを無効化する、(c)目的との学習済み対応を無効化する、のうち、その段で必要な比較だけを行う。無効化で新たな失敗を強制するために合法な代替経路を取り去らない。残った経路で再発見できるなら、その事実を含めて報告する。

「経験がなければ発見できなかった」は、無制限の計算やあらゆる既成方式についての不可能性ではなく、**指定した強い対照群・入力・予算の下で、経験に依存して形成・使用された区別が未見成績に寄与した**という操作的な主張に限定する。FULLとFRESHが同成績でも経験の価値はあり得るが、逐次改訂固有の優位は未実証のままとする。

## QB6 — 最初のHTMLは、実用下書き帳と記録器まで

### 最小構成と境界

| 含めるもの | 最小の挙動 |
|---|---|
| 本文入力 | 日本語IMEの使える通常のtextarea。一つの下書き、任意のタイトル・目的。普段のコピー＆ペーストを妨げない |
| 記録の可視化 | 「この本文の編集を記録中」、未保存・保存済み・保存失敗、取得欠損を表示。OS全体の記録ではない |
| 履歴表示 | 確定イベントごとの前後差分、順送り・巻戻し。再生は読み取り専用で、原履歴を改変しない |
| 区切り・復元 | 「保存して区切る」でrevision確定。自動のローカル退避を併用し、次回は同draftの続きとして開ける |
| 書き出し・読込み | 1エピソードをJSON、複数件をJSONL。本文だけのTXTコピーも可能。読込みは版・型・サイズ・再生一致を検査し、原本を上書きしない |
| ローカル削除 | 本文・履歴・派生索引の削除範囲を明示し、対象draftを削除できる。書き出し済みファイルは別物と表示 |

初版に含めないものは、学習・補完・自動訂正、SNS投稿、アカウント連携、クラウド同期、第三者解析、形態素解析、レンダラ、3D言語、汎用プラグイン機構である。「自動訂正候補を出す」は段1以降の別制作範囲で、初版の完成条件に混ぜない。HTMLのコードエディタではなく、HTMLで動く文章エディタを作る提案である。

### 記録、保存、プライバシー

`beforeinput / input / composition / selection`等のエディタ内イベントから、QB2の確定差分を作る。keydownはショートカットの制御に必要な範囲で扱っても、汎用のキー列を永続保存しない。貼付けた本文は記録に入るが、貼付け元のアプリやクリップボードの他の内容は集めない。選択移動は重複をまとめ、休止時間は相対時刻として残す。一定数の確定編集ごとと保存時にsnapshotを置き、再生コストと容量を制限する。

配布するHTMLはローカルで完結し、外部フォント・CDN・解析タグ・APIを使わない。通信を必要とするコードを入れず、通信禁止のCSPも検討し、実装検証で通信がないことを確かめる。本人の文字列はHTMLとして解釈せず、文字として表示する。JSON読込みからスクリプトを実行する経路も作らない。

既定のデータ保存先はOwner端末のブラウザ内保存領域と、本人が書き出したローカルJSONファイル。配布物や公開GitHubへ、実入力の本文・削除前の本文・機械提案への評価を載せない。ChatGPT/Museへデータが自動的に届く設計にはしない。調査・研究用に渡す場合は、本人が選び、**削除された文字も含む履歴全体**を確認した別コピーだけを手動で共有する。最終文だけの匿名化では不十分である。

ブラウザ内保存はバックアップではなく、私的な暗号保管庫でもない。初回に保存可否を試し、未対応・容量超過・file起動時の挙動差があれば「未保存」を明示し、JSON書き出しを使う。安定した実行方法はOwner端末で確かめてから決める。書き出しや端末バックアップがない状態で「安全に保存済み」と表示しない。認証情報等の秘匿文を意図せず入れた場合に備え、そのdraft全体を履歴ごと削除できるようにする。

実用の保存版と、研究の学習用・保留用コピーは別管理にする。公開repoに置くのは架空のfixtureと仕様のみ。個人用の学習済み規則・記憶にも固有名詞や削除済み表現が残り得るため、原文と同じローカル扱いにする。

### 作る人・確かめる人・使う人

制作許可後、ChatGPTがHTML一枚と少数の架空の確認例を作る。監督者は、IME確定／中止／再変換、絵文字、改行、範囲置換、貼付け、undo/redo、再読込み、保存失敗、欠損表示、削除、ネットワーク通信なしを確認する。ブラウザの内部IME・undoを全部自前実装することは求めず、観測できない部分は欠損として扱う。

Ownerは手元の普段のブラウザで、短い非個人的な文を一度書き、閉じて復元し、JSONを再読込みする確認を5〜10分程度行う。その後は普段の下書きに使うだけとし、一文ごとの注釈、単語分割、正解ラベル付けは求めない。余分な操作は原則「保存して区切る」1回、目的の記入は任意。後日の候補確認は週5分以内を目安にする。

制作・受入の変更単位は一つの小さなエディタを基本とし、入力器・台帳・学習器を先に多段PRへ分けない。工学的に書いて保存できる段と、学習候補を作る段の間でOwnerが範囲を選べるようにする。

### 2〜4週間の供給見込み

使用頻度はまだ観測されていない。**週3〜5日に1日1件、3〜10分程度の短い実用下書きを書く場合**、2週間で6〜10件、4週間で12〜20件になる、という条件付き見込みを置く。これは実績ではなく、普段のメモや下書きのうち一件を移す想定からの算術である。数十・数百件の新規作文を頼まない。

このうち訂正付き・再生可能・共有可能・学習に使える件数は別で、反復する訂正がゼロの可能性もある。件数を増やすために一つの下書きを分割しない。最初の利用例は「SNSへ出すつもりの短文をここで書く→本人が直す→保存→必要なら本文だけコピー」で、投稿操作は本人の普段のアプリで行う。未投稿・途中放棄も有効な観測として残す。

### (b) 失敗条件と縮小・転換

路線全体を研究として続ける条件は、目的ある供給、検証可能な外部化、未見での寄与、本人に分かる成果の四つが順につながることである。E1が便利でもE3が成立しなければ、下書き帳としては成果、操作言語が育つという仮説は未支持、と分けて終えられる。停滞時に抽象カードや第二領域を無制限に追加することを継続条件にはしない。
