## 0. 本書の位置づけと到達点

S0の成果物は、独立の読者が「同じ入力をどう形にし、訂正後の何を保存し、何を一致とするか」を説明できる小仕様である。以下の「必須／拒否」は**採用後の実装が守る契約案**であり、実装済み・凍結済みという意味ではない。今回はこの文書だけを提出する。HTML、モデル、STL、教材、実行器、実験は作らない。

採用済みM1〜M10を前提に、最初の道具を「断面ロフト工房」とする。Ownerは言葉で指示し、前後を見て採否と任意の一言を返す。コード、頂点編集、長い注釈を要求しない。既存対話でAIが用意した変更JSONをHTMLで読む方式を維持する。Blender、新規有料API、専用GPU、常駐サーバを必須にしない。

G1／G2のみが登録対象。S0の受入からS1／S2の制作開始、G3／G4登録、各企画への接続を自動的に導かない。DekaSugiの現行本線（文と訂正）、Maccho／Morphoacoustics／hapticsの現行フェーズと凍結契約は変更しない。文書1件という今回の指定に従い、INDEX／ARCHの編集も含めない。索引更新は後の統合判断で扱う。

## 1. 対象例・対象外例

対象は、z軸上の同心・軸に直交する楕円断面2〜8個を、半径の区分線形補間でつないだ、両端開口の内腔境界1個に限る。通常の例は4〜8断面、最小の意味確認例は2断面でよい。「管」は内腔を囲う境界を意味し、材料の壁厚は持たない。

| 区分 | 具体例／要求 | 扱いと理由 |
|---|---|---|
| 対象 | 半径10mm、z=0／20／40／60mmの4円断面 | 一様な管状境界。端は開口。円は楕円の二半径が等しい場合 |
| 対象 | 同じ列のz=20mmだけx半径を10→8mmにする | ASTの1パラメータ変更。影響は隣接2区間へ広がるが、端の値は不変 |
| 対象 | x半径10mm、y半径6mm等の同方向の楕円列 | 非円形断面。軸の曲がり・断面のねじれはない |
| 入力拒否 | 半径0／負、z重複／逆順、同じsectionの重複参照、断面1個 | 面が潰れる、又は列の意味が未定義。暗黙の並べ替え・clampをしない |
| 未対応 | 中心が横にずれる、中心線が曲がる、断面が回転する、途中で枝分かれする | 本subsetで表せない。近似形へ黙って置換しない |
| 未対応 | 任意メッシュ、boolean、複数部品、全身、rig、sculpt、閉端 | 4演算以外の能力。新しい版・別仕様が必要 |
| 別の派生用途 | 印刷用の内外壁・環状端面、解析用の仮想端面、STL／GLB | S0の正本とは別物。S3で用途を選び、必要な検査を定める |
| 未認定 | 声道として正しい、発声できる、触感が正しい、印刷できる | 幾何が一致しても物理・生体・印刷の妥当性を意味しない |

開口は成功し得る仕様であり、watertightでないことだけでinvalidにしない。`inner_boundary`、将来の`analysis_closure`、`print_wall`、`display_mesh`を混同しない。S1の出力用途は`inner_boundary`のみ。3D viewerで裏面も見せる場合も、実際の壁を追加したとは扱わない。

## 2. 座標・単位・型と正本

### 2.1 数値と座標

| 項目 | 契約案 |
|---|---|
| 座標 | 右手系。zは長手方向、x／yは断面平面。全section中心は(0,0,z)。最初のz=0、以後は厳密増加 |
| 単位 | programと幾何観測はmm、面積はmm²。mm→mの暗黙変換は禁止。将来の受渡しadapterで明示する |
| 長さ型 `LengthMM` | JSONでは小数3桁の非負10進**文字列**。例 `"0.000"`, `"8.000"`, `"60.125"`。整数部は0又は先頭0なし。指数、符号、空白、単位の追記、JSON数値は拒否 |
| 演算時 | 文字列を整数の0.001mm刻みへ厳密変換し、補間・三角関数時だけmmのbinary64へ変換する。入力値を丸めて受理しない。-0、NaN、Infinityは存在しない型にする |
| 有効な寸法域 | zは0〜500.000mm、隣接z差は0.001mm以上。各半径は0.001〜100.000mm。これは本仕様の対象範囲案で、解剖学的な範囲ではない |
| ID型 | node／part／event等のIDはASCII `[a-z][a-z0-9_-]{0,47}`。同じ名前空間で一意、表示文とは別。ノードIDを並べ替えて別の形にしない |
| その他 | enumは完全一致、整数型へboolを代用しない。未知フィールド・重複JSONキー・未知演算・循環・未解決参照を拒否 |

長さを文字列にする理由は、入力と訂正のold値をJS／Python間で同じ刻みとして照合するためである。画面では「8mm」と読みやすく表示してよく、Ownerにこの表記を手入力させない。0.001mmは記述の刻みであり、物理精度・製造精度の保証ではない。許容誤差と記述刻みも別である。

## 3. S1用4演算の意味

| 演算 | 入力→出力型 | 固定する意味／拒否例 |
|---|---|---|
| `ellipse_section` | `(z_mm, radius_x_mm, radius_y_mm): LengthMM³ → Section` | 中心(0,0,z)、半軸a=x半径、b=y半径。半径は正。角度θ=0は+x、+z側から原点方向を見ると反時計回り。中心／回転／全径という別解釈はしない |
| `section_set` | `ordered unique Section refs[2..8] → SectionSet` | 配列順とzの厳密増加をともに要求する。最初はz=0。sort、重複統合、欠けた断面の補作をしない |
| `loft` | `(SectionSet, linear_radii, open) → OpenLumenBoundary` | 隣接断面間で**二半径を線形補間**する。面積の線形補間・spline・端の外挿はしない。端は元の断面の開口を保つ |
| `label_part` | `(OpenLumenBoundary, part_id, inner_boundary) → LabeledBoundary` | 形を変えず境界全体へ安定part IDを付ける。断面IDは生成来歴として併記。面番号を永続part IDにしない |

### 3.1 補間と端

区間z_i≤z≤z_(i+1)で `t=(z-z_i)/(z_(i+1)-z_i)`、`a(z)=(1-t)a_i+t a_(i+1)`、`b(z)=(1-t)b_i+t b_(i+1)`。境界は `(a(z)cosθ, b(z)sinθ, z)`、θ∈[0,2π)。内部の節点の値は両側で同じ。区間選択を一意にするため内部節点は右区間に属し、最後の節点だけ最終区間の右端とする。区間外zの問い合わせは`out_of_domain`、外挿や端値の延長はしない。

断面積の正本観測は `A(z)=πa(z)b(z)`。二半径を同時に変えると面積は一般に二次であり、面積そのものを線形補間した値と区別する。補間は位置連続だが半径の傾きは節点で折れてよい。滑らかな声道や実組織の境界を保証しない。

両端に円板・蓋・厚みを自動追加しない。入口／出口という生理的意味も付けず、`z_start`／`z_end`と呼ぶ。法線は内腔領域から外側へ向く約束とし、人体の材料表面の法線へ無条件に転用しない。体積・音響境界・印刷適否の観測はS1では`not_applicable`。

### 3.2 表示メッシュと観測

標準分割はN=32。リングは**入力したn個の断面位置のみ**とし、軸方向の中間リングは足さない。頂点番号は `v(i,j)=32i+j`、θ_j=2πj/32、j=0..31。継ぎ目頂点は複製せず、`j1=(j+1) mod 32`とする。各区間i=0..n-2、各jの順に次の2三角形を置く。

- `(v(i,j), v(i,j1), v(i+1,j))`
- `(v(i,j1), v(i+1,j1), v(i+1,j))`

Nは4の倍数なので±x／±yの極値が含まれる。三角形の向きは内腔から外向き。入力nに対し頂点32n、三角形64(n−1)、境界辺64本（両端に32本ずつ）、端ループ2個を期待する。4断面なら128頂点／192三角形、8断面でも256頂点／448三角形であり、2万三角形を初回の使用目標にしない。

楕円の解析境界と三角形の表示は別の表現。リング断面の多角形面積は `A_poly=(N/2)ab sin(2π/N)`、N=32で `A_poly/A=sin(π/16)/(π/16)≈0.993587`。解析面積との差約0.641%を不具合扱いしない。区間途中の三角形切断面が同じN角形になるとは仮定しない。途中面積は解析境界から算出し、メッシュsliceの別検証へ流用しない。

必須観測は、断面パラメータ表、節点と各区間中点の面積（2n−1点）、解析AABB、固定三面図（xz／yz／xy）、選択断面のxy図、前後差分表、実行状態である。AABBはx=±max(a_i)、y=±max(b_i)、z=[0,z_last]。ビューの軸・視線・尺度・選択断面・表示法の版を観測記録に含める。三面図と表を基本出口とし、WebGL表示不能でもこれらは残す。画像のピクセル完全一致は幾何の再生条件にしない。

## 4. 型付き編集、採否、保存

形の4演算と編集イベントを分ける。S1の通常訂正は`replace_param`、形状列の変更に必要な入口だけを以下の意味で定める。任意JSON Patchや任意JS／Pythonの実行は認めない。

| 編集 | 許可する意味 |
|---|---|
| `replace_param` | 既存sectionの`z_mm / radius_x_mm / radius_y_mm`いずれか1個について、oldとnewのLengthMMを指定。old一致を必須とする。`op`や版の書換えには使わない |
| `add_node` | 4演算の完全な型付きnodeを新IDで追加。最終的に孤立nodeが残るtransactionは拒否 |
| `reconnect` | ssのsections配列、loftのsections参照、labelのgeometry参照のいずれか全体をold／new指定で置換。順序検査・型検査をやり直す |
| `remove_node` | 対象nodeの完全なold値を照合して削除。transaction完了後のdangling参照は禁止 |
| `set_output` | 旧outputと新outputを指定。新outputは有効なlabel_partであり、全体の単一ロフト制約を維持 |

複数編集はordered transactionで順に一時状態へ適用する。中間状態の参照欠けは許すが、各編集の対象・old・型は適用時に照合し、**最終状態全体**の型・参照・寸法・予算検査が通るまで一括commitしない。失敗なら確定programは一切変えず、失敗した提案と理由を残す。rename、labelの変更、版変更はS1訂正入口では未対応とする。

変更JSONは`patch_schema_version / proposal_id / base_program_hash / language_version / edits`を必須にし、別のprogramを基準とした変更を拒否する。提案元`creator`（AI／人／道具の種別と利用時の版）はjournalへ残す。初回の既存対話とのやり取りではprogramと必要な指示のみをOwnerが渡し、アプリから自動外部送信しない。

提案の実行成功とOwnerの採用は別である。有効な候補も採用まではpreview。Ownerの`accept / reject / defer`を別イベントにする。reject／deferでは確定headを動かさない。undoは以前の有効program hashを新しいheadにするイベントであり、間の履歴は削除しない。空の理由は許し、AIがOwnerの理由を補完しない。

### 4.1 正本の照合と版

正本program、patch、イベントのpayloadに共通の自前canonical規則C0を置く。object keyはASCII昇順、array順は保持、空白なしUTF-8、改行なし、文字列は`"`／`\`／制御文字だけをescape（制御文字は小文字hexの`\u00xx`）、それ以外のUnicodeはそのまま、Unicode正規化はしない。数値は非負の安全整数のみ、長さは§2の固定文字列。null／boolは型が許す位置に限る。重複keyはcanonical化より先に拒否する。canonical bytesへSHA-256を取り、`sha256:`＋小文字64桁で参照する。元ファイルbytesのhashも別に残す。

`language_version / semantics_digest / geometry_profile_version / runtime_build / tessellation_profile / evaluator_version / episode_schema_version / canonical_version`を別項目にする。program hashはprogramだけ、runtime等はepisode実行manifestに置く。semantics_digestは採用した意味定義・定数・C0・適合例を束ねる意味manifestのdigest、runtime_buildは実装sourceの同定値とし、同じ意味を別実装が実現できるよう分離する。後の実装計画で両者の実値と対応する適合確認を固定する。現段階では未作成であり、ダミーdigestを認証値にしない。任意入力の自己申告digestだけを信頼せず、実行器が対応する版・digestとの対応を照合する。

未知版は`unsupported`、同名版でdigest不一致は`integrity_error`。暗黙更新はしない。移行が必要なら元program／bundleを保持したまま、新版と親hashを持つ別成果物を作り、旧版再生の成功に数えない。

### 4.2 journalと可搬bundle

初期は`model-episode/0`候補の単一JSON bundleでよい。DB、ZIP、画像の常時保存を必須にしない。論理的にはmanifest、hash→programの辞書、追記型events配列、任意assetsで構成する。

| 項目 | 最小契約 |
|---|---|
| manifest | episode_id、lineage_id、parent_episode（なければnull）、task_revision、初期／確定head program hash、各版、指示と出典、creator、全eventの末尾hash、終端状態、観測／資源／保存状態 |
| event payload | 連続seq（0始まり）、一意event_id、直前event hash（初回null）、分岐元event_id（なければnull）、actor、type、program_before／after、candidate_program_hash（なければnull）、patch又は採否等のpayload、execution_status、理由、observation_refs、資源状態 |
| event hash | event payloadのC0 bytesから算出。自身のhash値はpayload外に置く。直前hashと分岐元を分け、全順序とundo／訂正の意味の両方を保存 |
| program辞書 | 初期、全有効候補（却下案も含む）、確定headを重複排除して保持。不正入力はprogram扱いにせず失敗eventの提案payloadへ保持 |
| 観測 | program hash、実行manifest、表／ビュー設定を結ぶ。再生成できる画像は任意。資源計測が無ければ値null＋not_observed、ゼロにしない |
| 状態の別軸 | 終端`accepted / rejected / abandoned / open`、実行`valid / invalid / unsupported / resource_stop / not_run`、保存検証`complete / retention_incomplete / not_verified`を混ぜない |

`program_before / program_after`は常に**確定headの遷移**を表す。初期eventだけbefore=null／after=H0、その後の指示・提案・訂正・reject・defer・保存要求ではbefore=afterである。提案patchの結果はcandidate_program_hashへ置く。acceptは既存のvalid候補とそのbaseが現在headに一致する場合だけheadを候補へ移し、undoは記録済みの有効programへ移す。古いbaseの候補は、採否時にも拒否する。分岐元eventは必ず先行する同一episodeのeventで、訂正提案は却下元proposalを参照する。提案を却下しただけでepisode全体のterminal=rejectedにはしない。terminalはOwnerが制作の区切りを判断した状態である。

資源値は`wall_us / cpu_us / retained_bytes`の非負安全整数（最大2^53−1）、取れない値はnull＋not_observedとする。計測を整数μsへ丸める規則は最も近い整数、ちょうど半分は切上げとし、元計測の分解能も記録する。これは幾何数値を整数へ丸める規則ではない。自由文はUnicode文字列、壁時計は利用するならISO形式の文字列として保持し、head遷移の順序は壁時計ではなくseqを正本にする。

`integrity_error`はbundle／版／hash等の整合失敗であり、形のinvalidやOwnerのrejectとは別の再生報告に置く。読込失敗で現在の有効な制作状態を上書きしない。hash鎖は改変検出の仕組みであり、外部の独立保管やOwner本人の意思の認証ではない。

ブラウザ内journalの保存とファイルの持出しは別状態。ダウンロード要求だけで「保存確認済み」と表示しない。書出したファイルを別起動で読込み、§6を通った時点で、その読込みに対する`complete`の検証報告を出す。自己参照を避け、検証報告は対象bundleのraw hashを持つ別の実行記録にし、元bundleを書換えない。単一bundleに自分自身のraw hashを入れない。

未見領域は本票で生成・予約課題化しない。将来の予約manifestの参照欄（初期null）とlineageだけ用意する。評価用のsplit・目標・正解は別manifestへ置き、archive全体を後の学習器入力にしない。本票の公開紙上例は既知例なので将来のholdoutには使えない。

## 5. 1回の訂正と保存の紙上例

以下のP0／P1／P2とH0／H1／H2は説明用の記号で、実hashではない。実bundleでは完全なprogramと実算出hashが必要。§2.2をP0、H0をそのhashとする。

| 段 | 指示／イベント | 候補・確定headと残すもの |
|---|---|---|
| 初期 | Owner「中央寄りを少し細く。端はそのまま」 | 指示はzを一意にしないので、AIが「z=20mmのx半径のみ、端とy半径は保つ」と解釈案を提示。曖昧さを黙って正解化しない。head=H0 |
| 提案 | P0のs1.radius_x_mmを10→6mmにする候補P1 | patch／前後／観測を記録。P1はvalidだがpreviewのみ、head=H0 |
| **1回の訂正** | Owner「そこは細すぎる。8mmにして」 | reject P1と短文を保存。訂正先は画面で示したs1に紐付け、目標をgoal-v1のまま維持 |
| 訂正提案 | P0を基準に10→8mmとする候補P2 | P1を確定履歴へ挿入しない。P2の訂正元proposalをP1として記録。baseはH0、headはまだH0 |
| 採用 | Owner accept P2（理由は任意） | head=H2。P0／却下P1／採用P2と全eventsを保持。P1は不正入力ではない |
| 保存 | bundle書出し、別起動の読込みで照合 | 保存要求、持出し、再読込検証を区別。§6が通れば対象bundleの復元確認。未実測の時間・hash・画像を紙上で作らない |

訂正提案P2のpatch payload例は次である。`base_program_hash`等のplaceholderは紙上専用で、実読込では拒否される。

```json
{
  "patch_schema_version":"model-patch/0",
  "proposal_id":"proposal-2",
  "base_program_hash":"<H0: paper-only>",
  "language_version":"model-dsl/0",
  "edits":[
    {"op":"replace_param","target_node":"s1","field":"radius_x_mm","old":"10.000","new":"8.000"}
  ]
}
```

紙上の観測期待値（単位はmm／mm²）:

| 観測 | P0 | 却下P1 | 採用P2 |
|---|---|---|---|
| s1の半軸(a,b) | (10,10) | (6,10) | (8,10) |
| z=20の解析面積 | 100π | 60π | 80π |
| z=10／30の補間半軸 | (10,10) | (8,10) | (9,10) |
| z=10／30の解析面積 | 100π | 80π | 90π |
| z=0／60の半軸と面積 | (10,10),100π | 同じ | 同じ |
| AABB | x,y=[−10,10],z=[0,60] | 同じ | 同じ |
| メッシュ／部位 | 128頂点,192三角形,開口2,part=lumen-main | 同じ構成 | 同じ構成 |

AABBや頂点数だけでは訂正の再生を判定できない例でもある。採用P2は半径1パラメータだけの近接変更対となるが、改変の影響は0<z<40に広がる。端だけ保たれたことと、形が局所一点だけ変わったことは異なる。

追加の失敗経路は紙上の受入例として定める。new=`"0.000"`ならinvalidでH2保持、H0基準のpatchをH2へ再適用すればbase不一致、rejectならhead保持、undo(H0)なら新eventでH0復帰しH2も残す。途中終了ならterminal=open又はabandonedを実際の判断に応じて残す。これらを今回実行したとは主張しない。

## 6. 再生の照合条件とS0受入

再生は①保存された履歴の復元、②保存programからの幾何再構成に分ける。AIへ同じ自然言語を再度渡して同じ提案が返ることは求めない。保存済みの型付き提案・採否を再生する。

| 層 | 一致条件案 | 不一致／欠測の扱い |
|---|---|---|
| 原本・版 | raw bundle hashを報告。C0 program／event bytes、各hash、参照、版と対応digestを照合 | raw bytesが違っても整形差ならcanonical一致を別報告。未知版=unsupported、hash矛盾=integrity_error |
| 履歴 | 全seqとhash鎖、分岐元、before／after、各patchのold／base、採否・undo遷移を全件照合。初期から復元したheadがmanifest headと一致 | 最終programだけ一致しても履歴合格にしない。必須program／event不足はretention_incomplete |
| 型・構造 | 全programの4演算構造、値域、端=open、用途=inner_boundary、part IDが厳密一致 | 自動修復しない。却下valid候補も再構成対象。不正提案は同じ拒否分類を確認 |
| 接続 | 同じrings32-authored/0の頂点順・face列・part対応・n／N・端ループが厳密一致 | STLの並べ替え後の比較は本段に持ち込まない。分割変更は別profile、比較不能を明示 |
| 寸法・形 | 保存programから別実装で求めた節点／中点のa,b,z、頂点xyz、解析AABBの各成分について `abs(x−y) ≤ max(10^-6 mm, 10^-9 × max(abs(x),abs(y)))` | 1成分でも超えればgeometry_mismatch。無限・欠測は比較不能、成功に置換しない |
| 面積 | 同じ節点／中点の解析Aについて `abs(A−B) ≤ max(10^-6 mm², 10^-9 × max(abs(A),abs(B)))`。リング多角形面積は§3.2の式とも別に照合 | 解析値とmesh近似を直接同値としない。差を分割誤差と数値誤差に分ける |
| 観測 | program hash、表の採点点、ビュー設定と版を一致。図は同じ形／軸／尺度を示すか確認 | 画像raw hashは保管用。描画系やフォント差のpixel一致を必須にしない。画像欠測は明示 |
| 実行・保持 | 元実行の状態と今回再生の状態、時間・保持bytesとnot_observedを別々に記録 | 保存hash一致は速度・物理の認定ではない。実行を途中停止した場合はresource_stop |

上の許容差は**工学上の照合案**であり、将来の参考実装とOwner端末で適合性を確認する。精度が満たせなければ結果を見て同版の閾値を緩めず、原因と版改訂を別に審査する。geometry profileと対応版が同じであればruntime_buildが異なっても照合を試せるが、版文字列の一致だけを幾何一致の代用にしない。

S0の文書受入は、(1)対象／拒否／未対応を識別できる、(2)4演算の補間と開口端を再説明できる、(3)紙上例P2の80π／90πとhead遷移を追える、(4)履歴欠落・未知版・geometry_mismatchを成功にしない、(5)資源値が未実測の目安と分かる、の独立確認をもって判断する。S1の実装受入やS2の実復元確認はその後の別段である。

## 7. §6.2の資源目安の再確認

今回の再確認は**対象を縮めた設計上の再算定と測定計画**であり、Owner端末での計測ではない。端末の利用可能RAM、空き容量、OS／browser版、WebGL可否は本票では未確認。上位票の「numpyで0.6秒」は監督者VMでの別処理の報告であり、ブラウザの応答実測にしない。

| 上位設計の仮置き | S0での整理 | 後の実装計画／Owner端末で確かめること |
|---|---|---|
| 編集反応1秒程度 | 小さな変更JSON受理から型検査・表／図の更新完了までのwall目安として保持。AI対話／手渡し時間は別に記録 | 一様／狭窄／楕円の代表例で単発と連続操作、初回と通常時を分ける。最遅値と中央値を報告 |
| 保存／再読込10秒以内 | 書出し用データ構築、利用者のファイル選択待ちを除く読込み検査を別計時。人の待ち時間を性能値に混ぜない | 履歴が長い例、却下・undo・中断例。保存開始／要求／再読込確認を区別 |
| 円周32・軸8断面 | 標準N=32、n≤8。8断面=448三角形。32は表示profile固定、8は今回の対象境界案 | 最小2／通常4／最大8断面で比較。2Dの出口も確認し、遅い場合は新profileとして16分割等を検討 |
| 上限2万三角形程度 | **S1では不要**。448を越える入力を対象外とし、2万は後段の再検討候補へ戻す | 他の形状を選ぶまで高精細処理を足さない。これは性能capの実測確定ではない |
| 2MiB/episode程度 | program＋events＋任意代表画像のUTF-8等の実bytes合計。圧縮後サイズだけで判断しない | 1MiB=1,048,576bytes。画像なし／少数画像を分け、重複programをhash共有して計測 |
| 総保存256MiB程度 | pilotに割当て済みの空き容量ではない。Ownerの空きと希望保存量を確認後に予算案を決める | 一時書出し／再読込用コピーも含めたピーク占有を報告。256÷2=128件を蓄積ノルマにしない |
| CPU／メモリ／開発工数 | 上位票では数値未設定のまま。1.5CPU共有VMをOwner端末の代用にしない | OS／browser／runtime、wall、取れるCPUとメモリ、busy時の負担、bundleの増分量、開発範囲を実装計画に記す。取れない値はnot_observed |

対象境界（n、寸法域、許可演算）と、実測前の性能／保存予算の目安を分ける。後の実装計画で、入力bytes・events数・transaction長・保持量の具体的な検査上限と中断方法を、Ownerの空き・代表bundleサイズを基に定める。今回は固定capを新設しない。これらが未決のまま無制限のJSONを読み込む実装へ進めない。

後の測定はOwnerのノートPCのブラウザを主、共有VMの参照実行器を副として**別々に**扱う。タブレット対応は別の希望があるまで受入必須にしない。端末情報が必要な段でもOwnerへコード編集や測定器の実装を求めず、実装側が簡単な報告入口を用意する。具体的なRAM容量や空き容量を推測してcapを決めない。

最新確定編集だけを優先し、重い処理は要求時に1件。保存予算に近づいたら新規提案のcommit前に停止し、現在の有効状態と失敗／却下履歴を守る。保存失敗はretention_incomplete。縮小順は任意画像を減らす→2D優先→新しい低分割profile又は対象縮小。履歴削除、GPU購入、Kaggle継続無料枠を前提にした拡大はしない。
